- **状态**：**已实现最小闭环（2026-08-08）**；决策见 §9。代码：`packages/science/src/sandbox/*`，工具：`science_run` / `science_rollback`
- **日期**：2026-08-08
- **关联**：`AGENTS.md`（任意代码执行保持禁用，直到沙箱与 permission owner 存在）；`docs/science-platform-migration.md` §7.3 P3 / §11 P3

## 1. 背景与目标

个人科研场景需要 AI 能执行 Python/R/bash 代码（当前 P3 能力保持禁用）。目标平台为 **Windows / Linux / macOS**，并支持**无沙箱启动**。用户的使用形态是"完全信任模式"：全盘可读、可写项目与环境目录、可联网、**资源配额无限**（生信需要大内存与长时运行）、无需每次询问；同时要求 **audit（审计/进度回查）→ 人工判断 → abort（中止）→ rollback（回滚）** 的完整闭环。

本方案目标是：以**最小代码**建立一个**极宽松沙箱**，在满足用户全部使用需求的同时，满足项目规则（沙箱 + permission owner 必须存在），并把 P3 其余门槛合并为一个**最小闭环**。

## 2. 需求 → 沙箱策略映射

| 用户需求 | 沙箱策略 | 是否冲突 |
|---|---|---|
| 执行 Python / R / bash | 允许沙箱内运行解释器 | 不冲突 |
| 可写项目目录 + 环境目录 | 写入白名单：项目目录、环境/虚拟环境目录 | 不冲突（正是白名单语义） |
| 可读其他所有目录 | 全盘只读（read-only bind/挂载） | 不冲突（能读、不能改） |
| 可联网 | 放行网络 | 不冲突 |
| 无资源限制 | **资源配额无限**（生信大内存/长时运行）；abort 成为唯一停止机制 | 不冲突（用户决定） |
| 无需询问 | permission owner = 用户本人，默认自动放行（保留可配置开关） | 不冲突（owner 有权选择自动放行） |

## 3. 威胁模型：防什么、不防什么

**防（本方案的真实价值）**：
- AI 手滑/写错代码：误删、误覆盖、死循环、写满磁盘；
- prompt injection 造成的破坏性命令（恶意论文/网页/数据文件藏指令）。

**不防（用户已知情接受）**：
- "全盘可读 + 可联网"组合下的**故意数据外传**（如被下毒后读取密钥并外发）。沙箱按本配置无法拦截。

**结论**：这是"防事故"层，不是"防攻击"层；对个人科研工具是合理取舍。

## 4. 环境现状（2026-08-08 实测）

| 项 | 结果 | 影响 |
|---|---|---|
| Ubuntu 24.04，内核 6.17 | — | — |
| `kernel.apparmor_restrict_unprivileged_userns=1` | bwrap/unshare 默认被拒 | bwrap 需 1 行 sudo 或 AppArmor profile |
| podman rootless | 可用（已有本地镜像） | 可选提供方；但 docker.io 拉镜像网络不通 |
| python3.12 | 已装 | Python 可立即支持 |
| R | 未装 | R 需求出现时再装、再加白名单 |

> 注：Pi 自带 bash 工具当前即以宿主用户权限执行（无沙箱）。本沙箱针对的是**新增的 Python/R kernel/notebook 能力**（P3），不是给 Pi 现有 bash 加约束。

## 5. 跨平台与沙箱提供方策略

**技术事实**：轻量沙箱没有跨平台实现——bwrap 仅 Linux；macOS 的 Seatbelt 已废弃；Windows 的 Job Objects/AppContainer 不适用本场景；podman 虽跨平台但非 Linux 平台需后台跑 Linux 虚拟机（重、慢、依赖镜像网络）。

因此采用**可插拔沙箱提供方，默认无沙箱启动**：

| 提供方 | 平台 | 说明 |
|---|---|---|
| none（无沙箱） | 全部 | **默认**：直接以宿主权限运行（等价于 Pi 现有 bash）；audit/abort/rollback 闭环不受影响 |
| bwrap | Linux | **可选**（用户显式启用时使用；71KB 可随包携带）；需一次解锁（1 行 sudo 或 setuid 安装） |
| podman | Win/macOS/Linux | **可选**硬边界；需要 podman machine（非 Linux 平台为 Linux VM）+ 可用的镜像源 |

启动策略：**默认无沙箱启动**；Linux 上用户可显式选择 bwrap 沙箱。不做自动切换，由用户显式指定。

**打包**：每个平台各自编译一个单文件（Node SEA）：`medpi-run-linux` / `medpi-run-win.exe` / `medpi-run-macos`；bwrap 仅打进 Linux 包。跨平台编译不可行，需各平台各编一次。

## 6. 最小闭环（P3 七门 → 最小实现）

| P3 要求 | 本方案最小实现 |
|---|---|
| sandbox | 可插拔提供方：**默认 none（无沙箱）**；Linux 可选 bwrap；podman 可选 |
| 唯一 permission owner | 用户本人；"无需询问"= 默认自动放行，保留开关可临时改回逐次确认 |
| 资源配额 | **无限**（用户决定：生信大内存/长时运行）；因此 **abort 成为唯一停止机制**，必须可靠杀进程 |
| abort / cleanup | **需要**：用户基于 audit 人工判断后触发——杀整个进程组 + 清理临时目录/运行时产物 |
| redaction | **跳过**（个人使用无第三方读者）；仅保留"凭据不进日志/provenance"一句话纪律 |
| audit | **需要**：provenance 记 `run` 节点（命令/开始/结束/状态）+ 输出流式写入日志文件可回查；UI 可看进度 |
| rollback | **需要，已定（2026-08-08）**：两者结合——运行前自动 git 提交为“存档点”+ 隔离工作目录装临时产物；回滚 = `git reset` 回存档点 + 清隔离目录。**前提：项目纳入 git 管理（即 P1-3，待办）** |

> **交互提醒（已告知用户）**：资源无限时，若脚本内存耗尽，机器可能在 abort 生效前变卡。因此 abort 必须可靠（杀进程组、`--die-with-parent`），并建议（可选，非硬限制）加"内存软告警"，让 UI 在内存逼近阈值时提示，由用户决定是否终止。

## 7. 验收标准（最小，不 mock）

1. 沙箱内可运行 python，可写项目/环境目录；
2. 沙箱外目录只读：尝试写入被拒绝；
3. 运行中可随时由用户触发终止，进程组无残留、临时文件被清理；
4. 每次运行在 provenance 留有 `run` 记录（命令/开始/结束/状态），输出可回查；
5. 回滚可回到“运行前存档点”：被改/删的已跟踪文件被恢复，隔离目录本次临时产物被清除；
6. 测试覆盖以上行为，不 mock 文件系统/进程。

## 8. 非目标（Non-goals）

- 不做数据外传防护（用户已接受全读 + 联网）；
- 不做多租户/公网部署加固（P0/P1 保持搁置）；
- 不做 R kernel（未安装，需求出现时再加）；
- v1 不做 notebook UI；
- 不迁移 MedHorizon 的 kernel/notebook 实现文件（只做新薄封装）。
